# Personalization / AI Agent — актуальная схема

> Этот документ описывает текущую реализацию InstaWorm / Instalead. Старые термины `Targeted`, `Smart`, `AI Prompt` и прогнозы reply rate больше не являются частью фактического personalization flow.

## 1. Что происходит с каждым лидом

Персонализация двухступенчатая:

```text
Instagram profile
      ↓
Profile Enrichment
      ↓
Lead Intelligence
(summary + facts + 3 hooks + metadata)
      ↓
AI Agent context
      +
Lead Intelligence
      ↓
Personalization contract
      ↓
JSON package
      ↓
Quality Gate
      ↓
до 2 попыток
      ↓
готовый DM
```

### Этап 1 — Lead Intelligence

Расширение передаёт username, bio и информативные подписи постов. LLM должна создать структурированную заметку:

- `summary` — плотный конспект профиля, начинающийся с `В профиле`;
- `facts` — атомарные проверяемые факты;
- `key_signals` — конкретные сигналы;
- `what_does` / `niche` — только подтверждённые сведения;
- `possible_interest` — только осторожная гипотеза;
- `hooks` — ровно 3 конкретных повода для персонального DM;
- `avoid` — что нельзя утверждать или использовать.

Главное правило: **ни одной детали без опоры на исходный профиль**.

Если профиль бедный, система уменьшает объём заметки. Она не должна заполнять её общими фразами вроде «эксперт в своей нише».

Подписи постов являются полноценным источником фактов, а не просто запасным источником после bio.

## 2. Как проверяется конспект

До сохранения заметки система проверяет:

1. `summary` начинается с `В профиле`.
2. Summary не слишком короткий.
3. В нём есть реальные признаки исходного профиля.
4. Есть ровно 3 hooks допустимой длины.
5. Каждый hook имеет связь с исходными данными.
6. Очевидно шаблонные summaries отбрасываются.

Если batch дал плохой результат, профиль повторяется отдельно. Если заметка всё ещё слишком поверхностная, запускается dense rewrite.

Каждая заметка получает `ENRICH_VERSION`, evidence metadata и content hash. Из-за этого старый DM нельзя незаметно использовать после изменения конспекта.

## 3. Персонализационный контракт DM

Второй AI получает:

### Контекст бизнеса

Из вкладки **AI Agent**:

- компания;
- продукт;
- целевая аудитория;
- проблема;
- результат;
- оффер;
- способ доставки;
- proof;
- CTA;
- тон;
- пример сообщения;
- запреты;
- политика обращения по имени;
- порядок `profile_first / offer_first`;
- длина;
- язык.

### Контекст лида

Приоритет:

1. Lead Intelligence;
2. hooks;
3. bio / посты, если они доступны в текущем запросе;
4. остальные поля профиля.

Количество подписчиков не используется как персональный hook и не передаётся в AI Agent как блок `АУДИТОРИЯ`.

## 4. Формат ответа второго AI

Модель обязана вернуть JSON:

```json
{
  "personalization_hook": "конкретная деталь о лиде",
  "relevant_problem": "релевантная проблема или возможность",
  "offer_angle": "какая часть оффера здесь уместна",
  "cta": "один простой CTA",
  "final_message": "готовый DM"
}
```

`final_message` должен быть самостоятельным сообщением, а остальные поля нужны для контроля качества и истории генерации.

Нельзя одновременно просить модель вернуть JSON и «только текст сообщения». В текущем prompt contract оставлен только JSON-формат.

## 5. Логика сообщения

Базовая структура:

```text
1. Personalization
2. Relevant problem / opportunity
3. Offer
4. Proof — если есть и уместен
5. CTA
```

Но это **не означает, что каждый DM обязан механически содержать пять предложений**.

Модель может убрать блок, если он не нужен или для него нет данных. Она не может компенсировать отсутствие данных выдумкой.

Например, если в профиле нет подтверждения проблемы, можно сформулировать её как гипотезу или сразу перейти от конкретной детали к релевантному офферу.

## 6. Правило гибкости

Система должна быть жёсткой в фактах и гибкой в форме.

### Жёстко

- не выдумывать факты;
- не выдумывать интересы;
- не использовать неподтверждённые результаты;
- не использовать подписчиков как персональный повод;
- не копировать шаблон;
- сохранять смысл оффера и CTA;
- соблюдать язык и ограничения AI Agent.

### Гибко

- если нет хорошего hook — не имитировать знакомство;
- если profile data мало — писать нейтральнее;
- если конкретная структура не подходит лидy — перестроить фразы, не нарушая смысл;
- если proof отсутствует — не выдумывать proof;
- если имя неизвестно — не придумывать обращение.

## 7. Quality Gate

После каждой генерации проверяются:

- наличие текста;
- длина;
- запрещённые зачины;
- шаблонные клише;
- длинное тире;
- опора на Lead Intelligence;
- наличие CTA;
- язык;
- валидность JSON;
- отсутствие почти дословного копирования шаблона или примера стиля.

При провале причины передаются во вторую попытку. Вторая попытка должна вернуть полный JSON-пакет заново.

Если обе попытки не прошли gate, система логирует failure. Отправлять такой текст автоматически — отдельное решение продукта; gate не должен маскировать его как успешную генерацию.

## 8. Версии и stale messages

У каждого готового DM хранятся:

- версия AI Agent;
- версия Lead Intelligence;
- hash текущего summary/hooks;
- время генерации;
- hook/problem/offer angle/CTA;
- финальный текст.

Старый DM переиспользуется только если **все эти входные условия всё ещё актуальны**.

Если пользователь изменил AI Agent или пересоздал конспект, старый DM становится stale и генерируется заново.

## 9. Язык

Язык выбирается в следующем порядке:

1. явный параметр генерации;
2. настройка AI Agent, если язык задан явно;
3. автоматическое определение по профилю;
4. язык шаблона / fallback.

Автоопределение не должно определять французский, итальянский или португальский только по наличию `é` / `á` / `ú`: эти символы встречаются в нескольких языках. Используются слова, скрипт и отличительные признаки.

## 10. `use_smart_personalization`

Поле `use_smart_personalization` сохранено в БД для совместимости со старыми кампаниями, но **не является источником истины для текущего движка**.

Фактический режим определяется `personalization_mode` + настройками AI Agent.

В персонализированной кампании оффер берётся из AI Agent. `message_template` не является основным источником оффера.

## 11. Как правильно улучшать персонализацию

Если DM получается слабым, сначала проверяй в таком порядке:

1. Есть ли в Lead Intelligence конкретные факты?
2. Есть ли хотя бы один хороший hook из постов?
3. Правильно ли заполнен AI Agent?
4. Совпадает ли CTA с реальным действием, которое вы хотите получить?
5. Не слишком ли общая целевая аудитория?
6. Не заставляет ли custom instruction модель нарушать основной контракт?

Не нужно лечить плохую персонализацию добавлением всё более длинного prompt. Сначала нужно улучшить качество входного Lead Intelligence.

## Contact name source of truth

The contact's saved `full_name` from the Contacts table is the authoritative greeting name for AI personalization. The generator must never infer a greeting name from the Instagram username or replace the saved contact name with a scraped Instagram display name. If the contact has no saved name, do not invent one and do not use the username as a greeting.
